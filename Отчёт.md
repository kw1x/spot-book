# Отчёт по проекту SpotBook

## Доменная область приложения

SpotBook — сервис для бронирования рабочих мест и переговорок в офисе с гибким размещением сотрудников (hot-desking).

Основные задачи системы:
- Отображение плана этажа в виде интерактивной SVG-схемы.
- Проверка доступности столов и комнат на выбранный период времени.
- Создание и отмена броней без возможности случайных пересечений (double booking).
- Управление местами и их расположением на карте через админку.

## Стек реализации

- Бэкенд: Java 21, Spring Boot 3.4, Gradle, Liquibase, MapStruct, JJWT.
- Фронтенд: React, TypeScript, Vite, Tailwind CSS, Zustand, Lucide.
- База данных: PostgreSQL 16 с расширением btree_gist.
- Деплой: Docker, Docker Compose, Nginx.

## Основные сущности доменной области

1. User (Пользователь)
- id: UUID
- email: строка, уникальный
- password_hash: хеш пароля BCrypt
- full_name: имя и фамилия
- role: ROLE_USER или ROLE_ADMIN
- created_at: дата и время создания

2. Workspace (Рабочее место / Переговорка)
- id: UUID
- name: название (например, Стол А1, Переговорка Aurora)
- type: DESK или MEETING_ROOM
- capacity: вместимость (количество человек)
- floor: номер этажа
- pos_x, pos_y: координаты левого верхнего угла на плане
- width, height: ширина и высота блока на схеме
- is_active: флаг доступности места

3. Booking (Бронирование)
- id: UUID
- workspace_id: ссылка на рабочее место
- user_id: ссылка на пользователя
- start_time: начало брони
- end_time: конец брони
- status: CONFIRMED или CANCELLED
- created_at: дата создания записи

## Соответствие методологии 12 факторов

1. Кодовая база
Соответствует. Весь проект хранится в одном Git-репозитории. Серверная часть, клиентская часть и конфигурации запуска объединены в общую структуру.

2. Зависимости
Соответствует. Зависимости бэкенда зафиксированы в build.gradle, а фронтенда — в package.json. Никаких неучтенных системных библиотек не используется.

3. Конфигурация
Соответствует. Все изменяемые параметры и доступы к базе данных вынесены в переменные окружения (SPRING_DATASOURCE_URL, JWT_SECRET, SERVER_PORT и т.д.). В коде нет захардкоженных паролей.

4. Сторонние службы
Соответствует. База данных PostgreSQL подключается через сетевой URL. Приложение одинаково работает и с локальным контейнером, и с внешней базой в облаке.

5. Сборка, релиз, выполнение
Соответствует. Сборка и запуск разделены через multi-stage Dockerfile. На этапе сборки компилируется код, а в финальный образ попадает только готовый jar-файл и среда выполнения JRE.

6. Процессы
Соответствует. Бэкенд спроектирован без сохранения состояния (stateless). Сессии в оперативной памяти не хранятся, авторизация работает через токены JWT. Это позволяет запускать любое количество реплик приложения.

7. Привязка портов
Соответствует. Сервис сам слушает входящий порт (бэкенд — 8080 через встроенный Tomcat, веб-интерфейс — 80/3000 через Nginx). Сторонний сервер приложений не нужен.

8. Параллелизм
Соответствует. Так как приложение stateless, масштабирование выполняется запуском дополнительных контейнеров через docker compose up --scale.

9. Утилизируемость
Соответствует. Приложение быстро запускается и корректно завершает работу по сигналу SIGTERM (graceful shutdown), успевая закрыть текущие запросы и соединения с базой данных.

10. Паритет разработки и эксплуатации
Соответствует. И для локальной разработки, и для продакшена используется одна и та же СУБД PostgreSQL 16 в Docker. In-memory базы вроде H2 не применяются.

11. Журналирование
Соответствует. Приложение не пишет логи в локальные файлы на диске. Все логи идут потоком в stdout, откуда их забирает Docker.

12. Задачи администрирования
Соответствует. Схема базы данных обновляется автоматически при старте через миграции Liquibase. Ручные правки таблиц через консоль СУБД исключены.
